# Connections & Open Games — framework update design and work packages

**Revision 2.** Successor to the party model, driven by the 2026-08-16 field
test (`plans/connection-model-2026-08.md` — read it first). Revision 2 follows
a comparison with the fleet's flagship multiplayer game, **cardstock**
(`../cardstock`, `TABLES_PLAN.md` + `MULTIPLAYER_PLAN.md`), and supersedes
revision 1's host-side seat-map relay: the evidence below shows the transport
relay has no real consumer, so it is removed rather than rescoped. The file
name is historical; "table" turns out to be cardstock's word (see
Terminology), and this design deliberately does not take it.

Design stance, in one paragraph: users manage **connections** (durable,
symmetric, the flat Linked-devices list that already exists and worked in the
field test). Games get **open-game scopes** (per-connection, per-game,
symmetric, consent-gated, ephemeral). The framework's whole multiplayer job
becomes: direct links, per-game consent, roster/`onReady`/attribution, and
targeted or scope-fanned sends. **Routing between players is the game's job**
— cardstock already does it host-authoritatively, correctly, and its
`src/match/` kit is the designated reusable pattern (its T5 / the launcher's
parked WP-L2 `arcade-table`). The party — a pre-declared, persisted,
user-managed grouping — is deleted as a concept.

## Terminology

- **Connection** — a durable, symmetric device pairing (unchanged).
- **Open game / scope** — game *g* is open on connection *L*: both ends have
  consented to play *g* together over that link. Framework-owned, RAM-only.
- **Table** — *cardstock's* word, and it stays cardstock's: a game-layer
  object (per-pack, `tableId` on every frame, its own directory, seat stubs,
  persistence — `TABLES_PLAN.md`). The framework never uses "table" for its
  own concepts. Other games get tables by adopting the cardstock kit, not
  from the transport.

## Evidence: what the fleet actually uses

The party model's relay star was designed for guest↔guest games. A sweep of
every game repo that names `Arcade.peer` (cardstock and p2p-chat; no other
game touches the API):

- **Cardstock requires exactly three caps** — `peer.sendTo`, `peer.roster`,
  `peer.meta` (`src/match/peerPort.js:32`) — all of which survive this design.
- **Every gameplay frame is a targeted send over a direct link.** Clients send
  only to their host (`client.js:107`); hosts send per-seat
  (`host.js:122`). Host authority *is* the routing.
- **Cardstock already outgrew the one-hub roster.** `discoverHost`
  (`client.js:66-78`) documents "ONE DIRECT PEER IS NO LONGER THE ONLY SHAPE
  … the CALLER names the table it joined"; the sighting rule
  (`tableSightings.js:351-360`) is "AUTHENTIC MEANS from a device we hold a
  direct link to … the sender must be direct and the frame must not be
  relayed." It was built for a multi-direct world the party model actively
  suppressed.
- **The party layer actively harmed it**: a member's lobby broadcasts reach
  fellow members only via relay, which cardstock then *rejects as spoofed* —
  so a member-hosted table was sightable by the party leader and invisible to
  everyone else. Asymmetric discovery, by transport accident.
- **p2p-chat** is direct-links-only by its own comment (`app.js:192`) and
  sends everything `{to}`-targeted.
- **The single genuine relay consumer in the fleet**: a cardstock joiner's
  `emote` and `bye` are broadcasts "to the ROOM" (`client.js:112-124`) that
  reach fellow joiners only through the hub. Two cosmetic frame kinds. WP6
  makes them host-mediated — more consistent with cardstock's own authority
  model, not less.

Conclusion: transport relay, per-party roles, and the party object serve no
game. Delete them; do not rebuild them under a new name.

## Decisions (resolved)

- **D0 — Track-1 reconnect fix: unchanged from revision 1** (standby listener
  rings bounded by `standbyMaxAgeMs`; one resume predicate; surface 📞 Call).
  ⚠ *Veto point:* the ring's privacy delta — a passive broker observer sees
  sealed activity on daily-rotating topics where a standby device was
  previously silent.
- **D1 — Scope is the authority; gameId is a selector (security rule).** An
  inbound frame for game *g* arriving on link *L* reaches the local game iframe
  **iff *g* is open on *L***; otherwise dropped and diag-logged. The bridge
  **never forwards a game frame from one link to another** — there is no
  relay. Outbound: `send(payload, {to})` requires *g* open on that link;
  `send(payload)` fans to every link with *g* open (the sender's own direct
  links — host lobby/view broadcast keeps its exact semantics). `meta.relayed`
  stays in the API, now always `false` — cardstock's spoof check keeps running
  as defense in depth, and the cap contract (`peer.meta`) is unbroken.
- **D2 — Seating never requires players to be adjacent to each other — but it
  does require each player to be adjacent to the host.** Unchanged physics,
  now enforced at the game layer (cardstock's claim-seat rides the direct
  link). The dead end gets copy, not machinery: "Ask ⟨host⟩ to connect with
  ⟨device⟩."
- **D3 — Consent is layered, and the deep layer is the game's.** Accepting an
  invite consents to *playing g with that one device* (scopes are
  per-connection — accepting reveals you to the inviter alone). Who else is
  at a table is disclosed by the game's own lobby *before you sit down* —
  cardstock's seat grid already does this better than a launcher prompt
  could. The framework prompt therefore stays simple: "⟨name⟩ wants to play
  ⟨game⟩."
- **D4 — Invites are symmetric proposals.** Either end of a connection may
  propose opening *g*; the other accepts or silently declines. The host-side
  door proposes to **all live connections** that don't already have *g* open
  (no picker in the MVP); the joiner-side door ("knock") proposes to one. A
  per-connection "invites off" chip is a named fast-follow.
  ⚠ *Veto point:* a live backup pairing (the MacBook) sees "Paul wants to
  play Cardstock."
- **D5 — Only Hang Up mutates pairing state.** Closing a scope or a game
  never touches `paused`, auto-reconnect, or rendezvous records. `leaveParty`
  is deleted with its concept.
- **D6 — Migration is a read-time strip** of `knownPeers[dev].party`, plus
  the WP1d pair-store GC. Pairings, names, flags, secrets survive untouched.

## Target model

| | **Connection** | **Open game (scope)** |
|---|---|---|
| What | Symmetric pairing, direct link | Game *g* live on connection *L* |
| Lifetime | Durable | Dies with the link, the game, or an explicit close |
| Storage | knownPeers + rendezvous store | RAM only (`Map(gameId → Set(peerId))` in the bridge) |
| Created by | Ceremony (unchanged) | Invite proposal + accept |
| Roles | None | None — host/guest is the *game's* fact, per its own protocol |

**The game-facing contract after the change** (what GAME_INTEGRATION.md will
promise — chosen so cardstock and p2p-chat run unmodified):

- `peers()` for game *g* = devices with *g* open. **Every entry is
  `direct: true`, and there may be more than one** — the shape cardstock's
  `discoverHost` fallback and caller-named hosts already handle.
  Fellow-seat presence stays game-owned (lobby frames), exactly the
  thin-party principle.
- `onReady` fires per connection when *g* is open on it and the remote has
  the game mounted; re-fires on reconnect; idempotent. (Accepting an invite
  mounts the game, so accept → onReady cascades with no new machinery.)
- `fromDeviceId` attribution, exactly-once ordered delivery per link,
  `queue()` — all unchanged.
- Per-game `status()` derives from *g*'s scopes: `idle` until one is open.
  The availability gate games run at mount (`peerAvailability` pattern) is
  undisturbed.
- `peer.party()` resolves `null`, `parties()` `[]`, `attach(id)` `null` — all
  **already-legal answers** the SDK documents for the unattached case, so the
  cap can stay advertised with zero game-side breakage until WP5/WP6 retire
  the reads. No shim object needed.
- New cap **`peer.invite`**: `Arcade.peer.invite()` asks the launcher to run
  the D4 proposal flow for this game. Games feature-detect it like every
  other cap; without it the copy says "invite from the launcher menu."

What this deletes: transport relay + `relayed`-stamping fan-out, per-party
roles, `partyKeys`, `partyByKey`, `gameParties`, `partyStatuses`,
`indirectByParty`, `hubCapsByParty`, the party GC sweep, `adoptPartyId`,
party persistence, `leaveParty`, the party picker, the party cards, and the
Start/Join-a-party ceremony framing. What replaces it: one scope map, one
envelope family, one prompt.

## Work packages

### WP1 — Reconnect stability (independent — ship first)

Unchanged from revision 1. Files: `index.html` (~1540–1568), `arcade-p2p.js`
(`resumeRendezvous` ~2428), `p2p/rendezvous-episode-core.js` (SETUP_DONE ~430,
NUDGE ~494), `p2p/rendezvous.js`, carrier layer.

- **a. One predicate** shared by boot and resume gates; the log line states
  the branch and why.
- **b. Standby ring**: `standbyOnly` + listener role emits `armRing` at
  `SETUP_DONE` and on `NUDGE` (existing 5s rate cap), slow cadence, gated by
  `standbyMaxAgeMs`. Caller-role standby stays quiet. Unit tests in the pure
  transition table.
- **c. 📞 Call on the collapsed row** for idle + autoReconnect peers.
- **d. Hygiene**: pair-store GC (orphaned/superseded records — the field log
  showed 8 pairs for 4 devices); per-session carrier failure budget (a broker
  that has never connected stops redialing after N consecutive failures).

Acceptance: two profiles, `lastLiveSession` forced >6h, both cold-launched →
connected with zero interaction within one ring cadence.

### WP2 — Relay out, scopes in (`p2p/p2p-core.js` + `arcade-p2p.js` + PROTOCOL)

The merged package (see revision 2.1 above). Four stages in one PR, each
leaving the tree buildable; the suite is green at the end of stage 4, and the
`p2p-multiparty-acceptance` rewrite is what proves it.

**Stage 1 — transport subtraction.** Remove per-link `partyId`, `partyRole`,
`partyPeers`,
`closeParty`, `_gcParty`, `defaultPartyId`, the deprecated `isHost` mirror,
and the **entire relay/fan-out path including `relayed` stamping and inbound
`relayed`-strip** — no frame is ever forwarded between links again. p2p-core
becomes what it already mostly is: links, identity binding, resilience,
replay, signaling. `statusSummary()` loses its per-party breakdown (the
bridge now owns per-game reporting).

PROTOCOL.md §5.6 rewritten: game frames travel only on direct links between
consenting endpoints; scope admission is a bridge concern; `relayed` is a
reserved legacy field, never set.

Unit tests (`tools/p2p-core-unit.mjs`): relay tests replaced by their
negation — an inbound frame is delivered locally and **never** re-emitted on
any other link, whatever its payload claims.

**Stage 2 — bridge scopes.** Delete the seven party maps, sweep timer,
`adoptPartyId` resolver, party persistence, `leaveParty`. D6 migration strip
in `readKnownPeers`. Add the **scope map** `gameScopes: Map(gameId →
Set(peerId))` and the `'game'` launcher-envelope family (`invite` / `accept` /
`decline` / `close`) over the existing direct-link envelope channel. Link
death closes its scopes (nothing outlives its link); game leave sends `close`.
**D1 enforcement** both directions, with diag logging on drops.

**Stage 3 — game-facing surface.** Per-game status/roster/onReady from scopes
(the same per-game filtering the bridge does today, resourced;
`index.html:1257–1338` consumers adapt). Menu badge stays the aggregate.
`arcade:peer.party.op` answers null/[]/null; new `arcade:peer.invite` RPC
(the launcher prompt flow itself is WP4 — stage 3 lands the RPC and cap with
a minimal internal confirm so the acceptance suite can drive it). Cap list
gains `peer.invite`.

**Stage 4 — tests.** Including the **invariant test**: no code path other than
`hangUpKnownPeer` / `setKnownPeerRevoked` writes pause state — enforced by a
test, not a comment.

Acceptance: `tools/p2p-multiparty-acceptance.mjs` rewritten as
scope-acceptance: pair A↔B, A↔C; open game on both via invite; B and C each
see only A in the roster; a frame from B labeled with the game reaches A's
iframe and is never re-emitted to C; B knocks to open a second game
concurrently; scope death on link death; reconnect (WP1 machinery) restores
the link and a fresh invite reopens the scope.

### WP6 — Cardstock alignment — runs in `../cardstock`

**WP6a — independent of the launcher work, ship now:**

- **Host-mediated room announcements (cardstock protocol v3).** `emote` and
  joiner `bye` — the last two frames that assumed transport relay — become
  targeted sends to the host, which re-announces host-stamped

  model gets *more* consistent: everything a fellow joiner learns now comes
  from the host, like views and rosters already do. Clean
  `PROTOCOL_VERSION` bump per the §5 no-negotiation rule; works identically
  under the old and new launcher.
- Delete the two `party()` reads: the port's `party:` line
  (`src/match/peerPort.js:76`) and the `partyLabel` UI
  (`src/ui/party.js:652-665` — label falls back to connection/host names).
- Docs: MULTIPLAYER_PLAN §3's transport-contract bullets updated (party
  bullet → open-game scopes; "fellow joiners reachable but invisible" →
  "not reachable — and nothing here ever needed them"); note that
  `discoverHost`'s multi-direct handling and the sightings rule were built
  for exactly this world and are unchanged.

**WP6b — after launcher WP4:**

- `hostGame` / the "Play together" door: when availability passes but no
  scope is open, feature-detect `peer.invite` and call it (old launcher →
  existing "connect from the launcher menu" copy; no fallback protocol, per
  the peerPort philosophy).
- Joiner-side: on mount with zero open scopes, the same door knocks.
- `tools/peer-stub.mjs` gains a no-op `invite()`; `npm run mp-acceptance`
  (nine scenarios, three real launchers) re-run against the new launcher —
  this suite is the real integration gate for the whole redesign. Add a
  tenth scenario: the field-test shape — host invites two joiners who are
  not connected to each other, both sight the table, both seat, a move
  reaches both.

**Explicitly not in WP6:** cardstock's tables, directory, sightings, seat
stubs, persistence, timers — the entire #43 workstream is untouched. The
comparison's finding is that cardstock was already shaped for this framework;
the framework is the one catching up.

## Out of scope (explicitly)

- Transport relay as an opt-in service. Revision 1's host-side seat-map
  design (arrival-link-gated, gameId-as-selector) is the recorded shape if a
  future game ever wants transport fan-out — no current game does, and the
  cardstock kit is the preferred answer for the next multi-seat game.
- Per-connection "invites off" chip (D4 fast-follow).
- Extraction of the cardstock kit (`src/match/` T5) — stays a cardstock
  follow-up; WP5 only *names* it as the pattern.
- Any wire protocol version bump in the launcher (cardstock bumps its own
  game-layer protocol in WP6a; the transport wire is unchanged).
- The base45 QR payload stretch goal (still parked).
